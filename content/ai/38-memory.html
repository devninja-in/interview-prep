A model call is amnesia with perfect manners. Between requests it remembers nothing. When a user says “change that to Thursday,” the system only understands “that” if you bring the earlier turn back — or if you stored a structured fact and retrieved it on purpose. The model has no diary; if it feels like it remembers you, an engineer built the machinery that makes it so.

Memory design is deciding what to keep, where to keep it, when to write it, when to forget it, and what earns a seat on stage for the next prediction. It is data engineering wearing a friendly face — and, because it stores facts about people, it is also privacy engineering.

The product story and the failure it must prevent

A user tells a health assistant in January, “I’m allergic to penicillin.” In March, mid-conversation about a cold, they ask, “what can I take?” If memory works, the allergy is retrieved and the answer routes around penicillin. If memory fails, the model — with a clean, amnesiac context — cheerfully suggests amoxicillin. The opposite failure is just as damaging: the user said in one heated moment “cancel everything, I quit,” the system enshrines it as a durable preference, and weeks later the assistant is still acting on a mood. Memory engineering lives between these two cliffs — remembering the load-bearing facts, and not ossifying the noise — while giving the user the right to see and erase what is kept.

The model boundary for memory

Memory sits squarely on the boundary between weights and data. The weights must never be the store of user facts — they are frozen, shared across all users, and cannot be edited or deleted per person (a hard requirement under privacy law). So every durable fact about a user lives in an external store you own, and re-enters the model only as retrieved context for that user, gated by their identity. The model reasons; the store remembers. Keeping this split clean is what lets you honor a deletion request by deleting a row, rather than by retraining a model you cannot surgically edit.

Working memory: the live conversation

The current transcript is working memory — immediate and fragile, and it lives entirely inside the context window. When it grows past budget you have three moves that usually combine: slide a window of the most recent turns, summarize older turns into a running synopsis, and pin the load-bearing items (the goal, hard constraints, open tasks) so they never scroll away. The art is that pinning is a decision: an explicit constraint like “must be gluten-free” should be pinned as a fact, not left to survive the lottery of summarization.

Long-term memory: store outside, retrieve intentionally

Anything that must survive across sessions lives in a store you control: profiles, prior tickets, extracted facts, episode summaries. At turn time you retrieve only what is relevant — the same embedding idea as RAG, but the corpus is this one user’s history, scoped by their id. This symmetry is worth stating in an interview: memory is RAG over the user. The difference is the write path, the privacy stakes, and the need to reconcile facts that change over time.

The write path: what becomes a memory?

The read path is RAG; the write path is where memory earns its keep or ruins the experience. Not every sentence deserves storage. After a turn — usually in a background job so it does not add latency to the reply — an extractor proposes candidate facts, a dedupe/reconcile step compares them against existing memory, and only high-value, high-confidence facts are persisted with a timestamp, a source turn, and a confidence score. Prefer structured writes (timezone = "IST") over dumping raw chat, because structure is what lets you supersede and delete cleanly later. The failure to avoid: an over-eager extractor that saves every offhand remark, so the store fills with contradictory trivia and retrieval quality collapses. Less, but correct, beats more.

Conflict, decay, and forgetting

Users change their minds, and facts have half-lives. A new memory with the same key should supersede the old one rather than sit beside it — keep the old value with an end-timestamp for audit, but only the current value should reach the prompt. Attach time-to-live where it makes sense (“traveling next week” expires; “allergic to penicillin” does not). Let low-confidence, never-reinforced memories decay so noise fades while repeated signals strengthen. Forgetting is a feature, not a bug: a memory system that only accumulates will eventually contradict itself and bury the user’s real preferences under stale ones.

A day in the life of a memory write

User: “I’m traveling next week; ping me on WhatsApp.” After the turn, the extractor proposes {channel: "whatsapp", valid_until: next_week}. Reconciliation finds an older channel: "email" preference and marks it superseded (with an end date, not a delete). The profile UI shows the change so the user can veto it. Next session, retrieval pulls the new channel into pinned context before the model speaks — and when valid_until passes, the WhatsApp preference expires and email quietly returns. No romance, just a pipeline with a clock.

Storage architectures: vector, key-value, and graph

“Memory store” is not one thing; production systems usually blend three shapes, each matching a memory type. A key-value / document store holds structured semantic facts (allergy = penicillin, timezone = IST) — cheap, exact, trivially editable and deletable, and perfect for pinned profiles. A vector store holds episodic memories and free-text notes for fuzzy “what did we discuss about billing” recall — this is the RAG-over-the-user path. A graph store captures relationships (this user belongs to this account, which owns these tickets) when the value is in the connections rather than the text. The senior instinct mirrors RAG: do not add a vector database for facts that are really three columns in a table. Route exact, supersede-able attributes to key-value; route fuzzy recall to vectors; reach for a graph only when relationship traversal is the actual query. Whatever the shape, every record carries the same metadata — user id, tenant id, timestamp, confidence, source, TTL — so isolation, reconciliation, and deletion work uniformly across stores.

Budgeting the window like a producer

Everything competes for the same finite context, so ordering is policy. System policy is non-negotiable and goes first. Tool schemas are expensive but necessary for agents. Retrieved memories, RAG chunks, and chat history then contend for what remains. A practical order: policy → tool schemas → pinned profile → high-score retrieved memories → recent turns → older summary. Two watch-outs: the lost-in-the-middle effect means the most important pinned facts should sit near the edges, not buried mid-context; and every token of memory you add is a token of latency and cost you pay on every turn, so retrieve five relevant memories, not fifty.

Privacy, security, and user control

Storing facts about people is a regulated activity, and getting it wrong is a headline, not a bug ticket. The non-negotiables:

  • User-visible, user-editable memory. Users should be able to view, correct, and delete individual memories, and to turn memory off entirely. Trust is a feature; a silent, unaccountable “brain” is a liability.
  • Deletion that actually deletes. A “forget me” request must remove the row, its embedding, its backups within policy, and any derived summaries — GDPR/CCPA right-to-erasure applies to the memory store. Design for deletion from day one; it is painful to retrofit.
  • Tenant and user isolation. Scope every read and write by user and tenant id; a retrieval bug that returns another user’s memory is a data breach, not a relevance miss.
  • Encryption and minimization. Encrypt at rest, avoid storing secrets or special-category data unless essential, and never place memory into prompts that land in third-party logs without appropriate data terms.
  • Consent and provenance. Record where a memory came from so you can explain and defend it.

Evaluating memory quality

Memory has its own evals, distinct from RAG or generation. Measure write precision/recall (of the facts that mattered, how many were captured, and of what was captured, how many were correct and worth keeping); retrieval hit rate (when a stored fact was needed, was it surfaced?); staleness (how often the assistant acted on a superseded fact); and contradiction rate (how often memory disagreed with itself). Build a golden set of multi-session scenarios — “user states an allergy in session 1, asks for medication in session 3” — and run them as regression tests, because memory bugs only appear across sessions and will never show up in a single-turn test.

Summaries that do not lie

Running summaries drift: each regeneration can quietly drop or distort a detail until the synopsis contradicts the transcript. Mitigations: regenerate periodically from the last N raw turns rather than summarizing a summary; store decision bullets and explicit constraints separately from narrative color; and never let a summary erase a hard user constraint without keeping that constraint as its own fact row. A summary is a convenience; a constraint is a contract, and contracts do not live in prose that a future summarizer might paraphrase away.

Latency and cost

Keep the write path off the critical path — extract and reconcile in a background job so the user’s reply is not slowed by bookkeeping. On the read path, cache the pinned profile, cap retrieved memories to what the budget and quality justify, and remember that a bloated memory store is both a latency tax (larger searches, longer prompts) and a quality tax (more noise to rank through). The cheapest, fastest, and most private memory system is the one that stores the fewest correct facts and retrieves only the relevant ones.

When not to build memory

Memory adds real cost, privacy surface, and failure modes, so do not add it reflexively. Skip it when interactions are genuinely stateless (a one-shot translation or classification), when the “memory” is really durable business data that belongs in your system of record and should be queried directly rather than mirrored, or when the regulatory cost of storing personal facts outweighs the UX benefit. Often the right answer is a thin profile of a few explicit, user-set preferences rather than an ambient learning system — smaller, safer, and easier to explain. If you cannot commit to honoring deletion and isolation, do not store personal memory at all.

Real production example: ChatGPT memory, Mem0, and MemGPT

OpenAI’s ChatGPT memory is instructive precisely because of its controls: it extracts durable facts across chats, but it also shows users what it has stored, lets them delete individual memories, offers a memory-off “temporary chat,” and scopes memory per account — an acknowledgment that user control and isolation are core features, not add-ons. Purpose-built layers like Mem0 productize the extract-dedupe-reconcile write path so teams do not reinvent it, and the research system MemGPT framed long-term memory as an OS-style hierarchy, paging facts between a small in-context working set and a larger external store — the same tiered idea as swapping between RAM and disk. Across all of them the pattern holds: the model stays stateless, and an external, governed store does the remembering.

Multi-user and enterprise memory

Separate personal memory from organizational memory (playbooks, account state, team conventions). An agent acting for a team needs shared stores with roles and ACLs, while still isolating each individual’s private facts. In a design interview, draw two boxes — a personal graph and a tenant knowledge base — both feeding the same orchestrator under permission checks, and note that a memory written by one user must never leak to another through the shared store.

Interview close

Asked to “make the assistant remember users,” give the arc: the model is stateless, so all durable facts live in an external, per-user store and re-enter only as retrieved context — memory is RAG over the user, plus a disciplined write path. Describe tiers (pinned working set, episodic summaries, semantic facts), the extract → dedupe → supersede write pipeline running in the background, conflict resolution and decay so stale facts fade, and a window budget ordered by importance. Then lead with the parts juniors forget: user-visible edit/delete, real right-to-erasure, tenant isolation, and cross-session evals for staleness and contradiction. Expect follow-ups on how you honor a deletion request (delete the row, embedding, and derived summaries — never retrain), how you stop memory from ossifying a bad moment (confidence, TTL, supersede, decay), and when you would not build memory at all. Memory is how a stateless token engine starts to feel continuous — build it as governed data engineering, not as an invisible brain you hope the model already has.
