The product story and the failure it must prevent

An employee asks, "what did we promise customer X last quarter, and can you open a follow-up ticket?" The system that fails invents a promise that was never made, cites nothing, and either does nothing or files a ticket against the wrong account — an answer that is confident, unsupported, and occasionally destructive. The system that works retrieves the actual contract clause with a citation, refuses if the documents do not support an answer, remembers the customer from earlier in the conversation, opens the ticket only through a gated tool with the right account attached, and leaves an audit trail you can replay. Every component in this chapter exists to move behavior from the first story to the second: grounding kills the invented promise, memory supplies the "X" from context, the gated tool prevents the wrong-account ticket, and logging makes the whole thing accountable.

Requirements, said out loud

Before drawing boxes, state what the system must do — the discipline that separates a design from a diagram:

  • Answer from company knowledge with citations; refuse when unsupported.
  • Hold multi-turn context and durable preferences.
  • Take gated actions through tools (ticket, email draft, calendar hold).
  • Stay within latency and cost budgets; leave an audit trail.

Reads dominate, and correctness and traceability beat cleverness. That single observation shapes the architecture: it says grounding and citations come before autonomy, that most turns are cheap Q&A and only a few are expensive actions, and that being able to explain and replay an answer matters more than a marginally smarter response.

The model boundary, one last time

The design is only defensible if you hold the boundary that ran through the whole part: the model reasons and writes text, and nothing else. It does not store user facts (memory does, in an external store), does not hold knowledge (RAG supplies it at question time), does not touch systems (the orchestrator executes tools through MCP), and does not decide what is allowed (guardrails and authorization do). Draw that line clearly and the architecture almost falls out of it — each capability is just the external machinery that compensates for something the stateless token engine cannot do on its own. Blur that line and you get the failure stories: knowledge baked into weights that cannot be corrected, "memory" that cannot be deleted, tools the model can fire without a gate.

Architecture story

An orchestrator owns the turn. It assembles context (policy, profile, memories, RAG hits, skills), calls the model, and if the model requests tools, executes them through MCP servers, then loops. Each subsystem plays the role its chapter earned: RAG supplies knowledge, memory supplies continuity, skills supply procedures, MCP supplies actions and external data, and guardrails wrap the outside so untrusted input and irreversible output are both contained. The orchestrator is the one piece this part did not have a chapter for, and it is the real product — the conductor that decides what enters the context, in what order, under whose permissions, and what happens with the model's output.

A single turn, narrated

  1. Authenticate the user; load profile and permissions.
  2. Classify risk: Q&A vs action.
  3. Retrieve memories and RAG chunks filtered by ACL.
  4. Match a skill if the task is procedural.
  5. Call the model with tools available for this risk tier.
  6. If tool calls appear, execute, observe, and loop until final answer or budget exhausts.
  7. Validate output (schema, citations present, policy).
  8. Persist new memories and emit telemetry.

The order is not arbitrary. Authentication comes first because every downstream retrieval and tool call must be scoped to who is asking. Risk classification comes early because it decides which tools the model is even allowed to see this turn. ACL-filtered retrieval happens before the model call so the model never lays eyes on data the user cannot access. Validation and memory persistence come after, because output must be checked before it is trusted and only durable facts should be written. Walk an interviewer through this sequence and you demonstrate that you understand the turn as a pipeline of permission and validation, not a single model call.

PYTHON
def handle_turn(user, message, deps):
    ctx = deps.assemble_context(user, message)
    messages = deps.render_messages(ctx)
    tools = deps.tools_for(user, risk=ctx.risk)
    for _ in range(deps.max_steps):
        out = deps.model(messages, tools=tools)
        if not out.tool_calls:
            answer = deps.validate(out.content, ctx)
            deps.save_memory(user, message, answer)
            return answer
        messages.append(out)
        for call in out.tool_calls:
            deps.authorize(user, call)
            result = deps.mcp.call(call)
            messages.append({"role": "tool", "content": result, "tool_call_id": call.id})
    return deps.fallback_timeout()

Two lines carry most of the safety. deps.tools_for(user, risk=ctx.risk) means the model is only ever offered the tools appropriate to this user and this risk tier — a read-only question never even sees the delete tool. And deps.authorize(user, call) re-checks permission at execution time, so even if the model proposes something out of scope, the runtime refuses. The model proposes; the orchestrator disposes — the agent chapter's boundary, made concrete.

The customer-X question, traced through the whole stack

Run the opening question through the finished system and watch every chapter fire in sequence. The employee asks, "what did we promise customer X last quarter, and can you open a follow-up ticket?" First the orchestrator authenticates the employee and loads their permissions — they can read customer X's account, so retrieval will be allowed to surface it. Risk classification splits the request in two: a Q&A part ("what did we promise") and an action part ("open a ticket"), and only the action part will unlock a write tool later. Memory contributes the resolution of "X" and "last quarter" from earlier in the conversation, so the model is not guessing at the referent. RAG retrieves the actual contract and email chunks — ACL-filtered to what this employee may see — and the generation contract forces a cited answer, or a refusal if the documents do not support one; there is no invented promise because the model is only allowed to speak from what was retrieved. With the Q&A grounded, the model proposes a create_ticket call; because the turn was classified as an action, that tool was in scope, but authorize still re-checks that this user may open a ticket on this account, and — since filing a ticket is a real side effect — a confirmation gate surfaces the draft for approval. Only after the human clicks does MCP forward the call to the ticketing server, which returns a real ticket link. The orchestrator validates the final response (citations present, schema valid), persists any durable new fact to memory, and logs the entire turn for replay. Every failure from the product story was blocked by a specific component, exactly where the architecture promised it would be.

Reliability: guardrails and evals

Ship with prompt-injection defenses (treat every retrieved document and tool result as untrusted data that may carry instructions), PII scrubbing where needed, allowlisted tools, and human approval for irreversible actions. Then prove it works with evals built per stage: retrieval quality (did we fetch the right chunks?), faithfulness (did the answer stick to them?), tool success (did actions do the right thing?), and end-to-end task completion. Add tracing so any bad answer can be replayed exactly — the same context, the same tool calls — because in a system this layered, "it gave a wrong answer once" is only debuggable if you can reconstruct the turn.

Cost and latency plot

Break the budget by stage: retrieval, rerank, model tokens in and out, and tools — then attack the biggest line. Cache embeddings and frequent retrievals, use a small model for routing and risk classification and reserve the large model for final answers, and remember that the agent loop multiplies cost by steps because the transcript grows each turn. In an interview, draw the sequence diagram with p50 and p95 targets per stage; naming the tail latency (p95), not just the average, is the detail that reads as senior, because it is the tail that determines whether the assistant feels reliable under load.

Threat model in one paragraph

Attackers will not attack the model directly; they will put instructions in the data it reads — uploaded PDFs, ticket descriptions, web pages, calendar invites — betting the model will obey them. Your defense is layered, not a single filter: treat all retrieved text as data rather than instructions, allowlist tools so a hijacked prompt cannot reach a destructive one, require confirmation for side effects so no injection can silently spend or send, strip or sandbox HTML, and monitor for anomalous tool sequences that signal a compromised turn. Stating this calmly, as a normal part of the design rather than an afterthought, is rare and immediately credible.

Rollout plan

Do not ship the whole stack at once. Ship read-only Q&A with citations first — the highest-value, lowest-risk slice — then add memory, then tools behind feature flags and allowlists once you trust the loop. Put eval gates in CI against a golden set so a prompt tweak or an index change cannot silently regress quality. Grow the skills library as support teams codify procedures. The point of the whole architecture is that it stays stable while the content — documents, memories, skills, tools — grows around it, so each new capability is a config change and an eval, not a redesign.

What "done" looks like in six months

A trusted internal assistant: 80%+ of policy questions answered with citations, an average of about two tool calls on action workflows, human approval on anything that sends or spends, a weekly eval report landing in Slack, and a skills library owned by the ops team rather than engineering. Notice what is not on that list: a smarter model. In a mature system the model is almost boring — the retrieval, the memory governance, the gated tools, the evals, and the audit trail are the product. That inversion is the whole lesson of the part: the intelligence is commodity; the system around it is where trust, safety, and value actually live.
