As agents take on bigger jobs, the tempting shortcut is to stuff every procedure — how to write a postmortem, how to process a refund, how to onboard a vendor — into one enormous system prompt. That collapses under its own weight: the context fills with instructions that are irrelevant to the task at hand, cost climbs on every turn, and the important guidance gets buried in the middle where the model reads it least reliably. Skills are the modular storytelling device that fixes this: folders of instructions and helpers that the agent loads only when a task actually calls for them.

If prompting is the model's control surface and tools are its hands, skills are its playbooks — the organization's know-how, packaged so it rides along with the agent without turning every request into a novel-length prompt. The core idea is deceptively simple and worth saying plainly: keep the default prompt small, and pull in depth on demand.

The product story and the failure it must prevent

A support team handles fifty distinct workflows — refunds, chargebacks, account merges, GDPR deletions, each with its own rules and edge cases. Put all fifty into one prompt and two things break at once: the window bloats to the point where latency and cost balloon on every trivial "reset my password" question, and the model, drowning in mostly-irrelevant procedure, starts blending rules across workflows — applying the refund window to a chargeback, or the deletion checklist to an account merge. The failure skills prevent is exactly this dilution: the model that "knows everything" ends up doing everything a little wrong. The opposite failure is just as real — a skill so vaguely described that it never loads when it should, so the hard-won procedure sits in the catalog unused while the model improvises. Skill engineering lives between those two: load the right procedure at the right moment, and nothing else.

The model boundary for skills

Skills sit on the data side of the boundary, and that is their entire advantage. A procedure is not baked into the weights; it is text you own, load, edit, and delete. That means when the refund policy changes, you edit a file — you do not retrain a model or wait for a vendor's next release. It also means procedures are auditable and reviewable: a domain expert can read exactly what the agent will be told to do, and a security reviewer can check it for unsafe tool use before it ships. Contrast this with fine-tuning, where the same knowledge would be diffused into parameters you cannot inspect, edit surgically, or roll back cleanly. The senior framing: skills keep organizational know-how as governed data, not as frozen weights, so it can change at the speed of policy rather than the speed of training.

What a skill is

A skill is typically a directory with a SKILL.md (or equivalent) describing when to use it and how to do the job, plus optional scripts, templates, and examples. The catalog shows the agent only a short name and a description; the full text loads on match, so the context window stays lean until a task actually needs the detail. The structure matters: the "when" is metadata for routing, and the "how" is the procedure the model follows once selected.

TEXT
---
name: incident-writeup
description: Use when drafting a postmortem from timeline notes.
---
# Incident writeup
1. Extract timeline events with timestamps.
2. Separate impact, cause, and fix.
3. Output Markdown with sections: Summary, Impact, Timeline, Root cause, Actions.
Never invent timestamps. Ask if gaps exist.

Read that last line carefully — "Never invent timestamps. Ask if gaps exist." A good skill does not just list steps; it encodes the failure modes and the guardrails a domain expert learned the hard way. The skill is where you put the "don'ts" that keep the model honest on this specific task.

Progressive disclosure

The mechanism that makes skills scale is progressive disclosure — a ladder of how much context you pay for. Always loaded: just the name and description of each skill (cheap, a line or two apiece). On match: the full SKILL.md for the one skill that fits. On demand: the heavy attachments — scripts, large reference docs, example corpora — only if the procedure reaches for them. That ladder is what lets an organization have five hundred skills without a five-hundred-skill prompt: the model always sees a slim menu, and depth arrives only when it is ordered. It is the same instinct as RAG and memory — retrieve what is relevant, not everything you have.

The clean answer: reach for a skill when the knowledge is a repeatable, policy-shaped procedure that changes over time and belongs to domain experts — precisely the thing you do not want frozen in weights or copy-pasted into every prompt.

Authoring tips

A skill is a piece of software that a model executes, so author it with the same rigor:

  • Write descriptions that mention trigger phrases and exclusions — the description is the router's only signal, so "Use when drafting a postmortem" plus "Do not use for security incident reports" beats a vague one-liner.
  • Keep steps imperative and testable — each step should be a checkable action, not an aspiration.
  • Include one worked example and the common failure modes — show the model what good output looks like and what mistakes to avoid.
  • Version skills — breaking changes need migration notes, because a skill is a contract other workflows depend on.

Matching quality

The hardest part of a skills system is not writing skills — it is selecting the right one. If two descriptions overlap, the agent loads the wrong playbook and confidently follows the wrong procedure. Sharpen selection with explicit exclusions ("Do not use for legal advice"), and for large catalogs add an embedding match over skill descriptions with a confidence floor: if the top candidate is not clearly above the runner-up, do not guess — fall back to asking the user which procedure to follow. Treat skill selection as its own evaluable component with its own metrics (did the right skill load? how often did the wrong one?), because a perfect procedure invoked at the wrong moment is worse than no procedure at all.

A skill load, traced end to end

Watch one turn. A user writes, "we had an outage this morning, can you draft the postmortem from these notes?" The agent's context holds only the slim catalog — fifty skill names and one-line descriptions, a few hundred tokens total. The router matches the request against those descriptions and finds incident-writeup ("Use when drafting a postmortem from timeline notes") comfortably above the runner-up, so it clears the confidence floor without asking the user. Now, and only now, the full SKILL.md loads into context: the numbered steps, the required Markdown sections, and the hard rule "Never invent timestamps." The model follows the procedure, and when it needs to fetch the raw alert history it triggers an on-demand script bundled with the skill rather than carrying that data around all along. The postmortem comes back in the house format, every timestamp real. Notice the economy: forty-nine irrelevant procedures never entered the window, the one relevant procedure arrived exactly when it was needed, and its guardrail — not the model's improvisation — kept the output honest.

Lifecycle in an organization

Skills are where the org, not just the engineer, gets to teach the agent — so they need a lifecycle. A support lead drafts a skill after a messy incident ("here's how we should have handled that refund"). Engineering reviews it for unsafe tool use and for instructions that could be exploited. It ships behind a feature flag, accumulates eval cases ("refund within 30 days," "refund after 30 days," "refund on a fraudulent order"), and is versioned like code. When policy changes, you edit the skill — not the model weights, not a fine-tune, not a fifty-workflow mega-prompt. That editability by non-engineers, under review and evals, is the organizational payoff: the people who own the policy own the procedure.

Skills plus MCP and agents

Skills close the loop with the previous two chapters. An agent supplies the think → act → observe loop; MCP supplies the standardized tools; and a skill is the playbook that tells the agent which MCP tools to prefer, in what order, and how to interpret their results for this particular job. Skills are the playbook; MCP tools are the hands; the agent is the loop that runs them. Separating these keeps each editable by the right owner — domain experts revise playbooks without redeploying connectors, platform teams evolve MCP servers without rewriting procedures, and the agent runtime stays stable underneath both.

Latency, cost, and when not to use skills

Progressive disclosure exists because context is not free — every token of always-loaded skill metadata is paid on every single turn, so keep the catalog descriptions terse and push detail down the ladder. A bloated set of always-on skills is just a mega-prompt wearing a folder structure. And like the other chapters, skills are not always the answer: for a one-off instruction, a plain prompt snippet is simpler; for a fixed, deterministic workflow with no natural-language judgment, hand-written code is more reliable than a procedure the model interprets; and for behavior you truly want the model to internalize across every task, fine-tuning may fit better than a document loaded at runtime. Reach for skills when the knowledge is a repeatable procedure, owned by domain experts, that changes over time and only applies to some tasks — the sweet spot the mega-prompt and the fine-tune both handle badly.

Real production example: Claude's Agent Skills

Anthropic's Agent Skills productize exactly this pattern: a skill is a folder with a SKILL.md whose front-matter name and description stay resident while the body and any bundled scripts or resources load only when the task matches — progressive disclosure by construction. The design lets teams package organizational procedures (brand guidelines, document formats, internal workflows) as editable files that domain experts maintain, rather than as prompt text engineers copy around or behavior baked into a fine-tune. The lesson generalizes beyond any one vendor: the durable idea is the ladder — a slim always-on menu, full procedures on match, heavy resources on demand — plus the governance around it (review, versioning, evals) that turns a pile of instruction files into a maintainable capability.

Interview close

Asked "how would you let the org teach the agent new procedures without bloating the prompt," give the arc: cramming every procedure into one system prompt dilutes quality and taxes every turn, so package procedures as skills — folders with a SKILL.md describing when and how — and load them with progressive disclosure (name and description always, full procedure on match, heavy resources on demand). Distinguish skills from their neighbors: tools are capabilities, skills are procedures for using them, snippets are static text, and fine-tunes are frozen weights — reach for a skill when the knowledge is a repeatable, policy-shaped procedure that changes over time. Then lead with what juniors miss: skill selection is the hard part and deserves its own evals and a confidence floor with a fallback; skills live on the data side of the boundary so they change at the speed of policy, not training; and they need a real lifecycle — review for unsafe tool use, feature flags, versioning, migration notes. Skills are how organizational know-how rides along with the agent without turning every request into a novel-length system prompt — governed data, loaded just in time.
